# Agent Note: turn-nav 全量加载加滚动静默闸门（修复滚动闪动）

Status: implemented

## Problem

打开轮次导航面板后滚动聊天，页面会可见地跳动（「打开菜单，滚动，页面有
几率闪动」）。面板的打开即全量加载循环
（[分页大纲](../../implemented/feature/2026-08-27-turn-nav-paginated-outline.md)）
在打开时连续触发 `loadOlder()`：在报告会话上，八个分页（约 300 个消息
节点）在约 450 ms 内落地，聊天滚动区高度从 8465 px 涨到 26313 px，恰好
撞上读者开始滚动的时机。

聊天视图的两条路径与这些前置插入竞争：

- 内置的贴底跟随逻辑（`tipMoved && atBottom -> toBottom`）把每个历史批次
  都当作 tip 移动。刚从底部开始向上滚的读者（聊天后的常见姿态）
  `atBottom` 仍然锁存，于是每个落地的批次都把视口拽回底部。对运行中
  GUI 的只读 Playwright 探针确定性复现：四次运行每次都把视口拽回底部
  两次（+8409 px 与 +3973 px），此时读者正在向上滚。
- 滚动锚定补偿（原生锚定加聊天视图的锚行恢复）在端口静止时可靠，但在
  滚动手势进行中会被抑制或晚一拍重新武装，因此手势中落地的批次可能把
  内容推到读者眼皮底下。

两种失效都需要批次落进滚动手势窗口，所以用户看到的是概率性症状。

## Decision

`packages/turn-nav/src/client/TurnNavPanel.tsx` 的全量加载 effect 现在给
每次 `loadOlder()` 加了「聊天滚动端口静默」闸门（`SCROLL_IDLE_MS =
350`）：

- window 上的捕获阶段 `scroll` 监听记录最近一次滚动活动（scroll 不冒泡，
  捕获才能听到聊天滚动端口）。闸门刻意保守：文档内任何滚动都计入。
- 闸门在面板挂载时武装，因此读者打开面板后立刻开始滚动的窗口内，最早
  的几页不会落地。
- `lastScrollAt + 350 ms` 在未来时调用被推迟；`setTimeout` 到点后用
  `loadTick` 状态重新触发 effect（原有的进度/上限守卫不变）。

每个落地分页自身的补偿滚动（贴底重定位或锚定调整）会再次武装闸门，把
循环节拍到约每个静默窗一页。SDK 契约未动：`loadOlder` 依旧把历史分页
拉进共享会话窗口，只改调用节奏。

## Alternatives considered

- 退回按需分页（fa228e27 之前）：会丢掉页码真实总量——那正是全量循环
  存在的意义；SDK 不提供总轮数 RPC，翻到底是唯一获知总数的途径。
- 修聊天视图的补偿逻辑：锚行恢复与跟随逻辑属于官方
  `@deepseek-ai/dsh-client-ui-conversation` bundle，插件不得补丁宿主
  UI 行为。
- 只用固定延时节拍：定时器节拍的批次仍可能落在手势中；只有滚动活动
  信号知道何时前置插入对读者是安全的。

## Consequences

- 面板开着时读者滚动，历史加载暂停（pager 总数在完成前显示"..."），
  最后一次滚动事件约 350 ms 后恢复。打开面板不滚动时，第一页同样
  等一个静默窗，长会话上面板的「正在加载全部轮次」提示会稍久一点。
- 差分探针（同一会话，未修复与已修复 bundle）从每次运行两次贴底回拽
  降为零（共四次运行），八个历史分页全部落地、pager 到达真实总量。
- 残余风险：静默窗内发出的 `loadOlder`，其响应落地时读者恰好又开始
  滚动，仍可能手势中前置插入。该窗口只有一个宿主往返宽，且要求读者
  恰在其中开始滚动；没有宿主侧支持无法进一步消除。

## Testing

  通过（25/25）。新增回归用例「滚动时暂停历史加载、端口静默后恢复」
  （分步分页 store 上的伪时钟）在未修复面板上失败（loadOlder 立即被调、

  跳变（3/3 运行，每次 8 批次），pager 每次都到达真实总数。
